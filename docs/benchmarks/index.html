Detection benchmark

On the expanded 125-sample synthetic corpus (ten tools), overall precision is 100.0% and recall is 100.0% (76 true positives, 0 false positives, 0 false negatives). On the original 85-sample, 5-tool slice the same run scores precision 100.0% and recall 100.0% (was 91.5% / 84.3% in v0.38.0).

This is a small, author-written, synthetic corpus. It is not a red-team dataset, not drawn from production traffic, and not a claim about performance on real attacks. Heuristic scanners miss things; misses are listed on purpose.

How a detection is counted

A sample is counted as flagged when the assigned tool reports at least one finding with severity low, medium, high, or critical. Info-level inventory rules (for example SF12, FL10) are ignored. The script is benchmarks/run_benchmark.py; the labels live in benchmarks/manifest.json, benchmarks/heldout/manifest.json, benchmarks/redteam/manifest.json, benchmarks/redteam2/manifest.json, benchmarks/redteam3/manifest.json, benchmarks/redteam4/manifest.json, and benchmarks/redteam5/manifest.json, and benchmarks/redteam6/manifest.json, and benchmarks/redteam7/manifest.json, and benchmarks/redteam8/manifest.json. Fixtures are original and use only fake credentials and reserved documentation values.

Ten jobs are covered:

  • Prompt injection in tool results — resultguard
  • Poisoned MCP tool descriptions — toolpoison
  • Secret leaks — tracesweep (presence) and secretflow (propagation into later tool arguments)
  • Dangerous shell commands — shellfence
  • PII in transcripts — piiguard
  • SSRF / fetch destinations — fetchfence
  • Sensitive paths — pathfence
  • MCP client posture — mcpposture
  • Persistent memory poisoning — memfence
  • MCP OAuth metadata (round 2 only) — mcpoauth

Limits of this benchmark

  • Every fixture was written for this repository. A detector can look strong here and still fail on a real transcript format or a novel payload.
  • The corpus is still small (n=125 on the expanded set; n=85 on the original slice; n=40 held-out; n=100 independent red-team round 1; n=134 round 2; n=84 round 3; n=80 round 4; n=80 round 5; n=80 round 6; n=80 round 7; n=100 round 8). Percentages will move when a single sample is added or re-labeled.
  • The held-out set was written after the #7–#11 fixes and was not used to retune those rules. A strong held-out score is still not evidence of real-world robustness.
  • The independent red-team set was written without reading detector source or rule files. The v0.40.0 numbers on that set are the unseen score and stay visible. After issues #12–#16 were closed against general rule changes, the same set was re-run; those post-fix numbers are clearly labeled seen and are no longer independent.
  • Round 2 was the development set for the v0.43.0 generalization. Its v0.41.0 numbers stay visible as the unseen score. The post-generalization re-run is labeled seen.
  • Round 3 was the development set for the v0.44.0 generalization. Its v0.43.0 numbers stay visible as the unseen score. The post-generalization re-run is labeled seen.
  • Rounds 4, 5, and 6 were each written after the then-frozen rules and later became development sets; their original unseen scores stay visible and the re-runs are labeled seen.
  • Round 7 was written after the v0.47.0 rules were frozen and was scored once. Those numbers stay visible as an earlier unseen score.
  • Round 8 is a new independent set written by a separate author against the same frozen v0.47.0 detectors, without reading prior fixtures or detector source. It is the current unseen score, reported even when it is poor, and was not used to retune rules.
  • Info-level inventory findings are excluded. If we counted them, several tools would “detect” almost every transcript they parse.
  • All secrets and personal-data values are fake. tracesweep also suppresses documentation placeholders (the word example, your_api_key, and similar), which is why those values are not used as the malicious keys in this set.
