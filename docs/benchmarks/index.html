Detection benchmark

On the expanded 125-sample synthetic corpus (ten tools), overall precision is 100.0% and recall is 98.7% (75 true positives, 0 false positives, 1 false negatives). On the original 85-sample, 5-tool slice the same run scores precision 100.0% and recall 100.0% (was 91.5% / 84.3% in v0.38.0).

This is a small, author-written, synthetic corpus. It is not a red-team dataset, not drawn from production traffic, and not a claim about performance on real attacks. Heuristic scanners miss things; misses are listed on purpose.

Detection-gap issues #7–#11

The eight original evasions and four false positives were filed as #7 (resultguard), #8 (toolpoison), #9 (tracesweep), #10 (secretflow), and #11 (shellfence). The rule changes in this release are general (typo-tolerant and split-word override matching, ROT13 decode, multilingual override/exfil phrasing, soft workspace-dump-into-parameter, secret-prefix concatenation, encoded secret reuse, and pipe-to-shell deobfuscation), not string matches against the original fixtures. Those issues are closed against this release.

How a detection is counted

A sample is counted as flagged when the assigned tool reports at least one finding with severity low, medium, high, or critical. Info-level inventory rules (for example SF12, FL10) are ignored. The script is benchmarks/run_benchmark.py; the labels live in benchmarks/manifest.json and benchmarks/heldout/manifest.json. Fixtures are original and use only fake credentials and reserved documentation values.

Ten jobs are covered:

  • Prompt injection in tool results — resultguard
  • Poisoned MCP tool descriptions — toolpoison
  • Secret leaks — tracesweep (presence) and secretflow (propagation into later tool arguments)
  • Dangerous shell commands — shellfence
  • PII in transcripts — piiguard
  • SSRF / fetch destinations — fetchfence
  • Sensitive paths — pathfence
  • MCP client posture — mcpposture
  • Persistent memory poisoning — memfence

Limits of this benchmark

  • Every fixture was written for this repository. A detector can look strong here and still fail on a real transcript format or a novel payload.
  • The corpus is still small (n=125 on the expanded set; n=85 on the original slice; n=40 held-out). Percentages will move when a single sample is added or re-labeled.
  • The held-out set was written after the #7–#11 fixes and was not used to retune those rules. A strong held-out score is still not evidence of real-world robustness.
  • Info-level inventory findings are excluded. If we counted them, several tools would “detect” almost every transcript they parse.
  • All secrets and personal-data values are fake. tracesweep also suppresses documentation placeholders (the word example, your_api_key, and similar), which is why those values are not used as the malicious keys in this set.
