mcpoauth: detect weak OAuth settings in MCP server metadata in AI agents

Offline auditor for MCP server OAuth discovery metadata.

What it detects

Offline auditor for MCP server OAuth discovery metadata.

Remote MCP servers that require sign-in publish two JSON documents: OAuth 2.0 Protected Resource Metadata (RFC 9728, at /.well-known/oauth-protected-resource) and Authorization Server Metadata (RFC 8414 or OpenID Connect discovery). MCP clients trust those documents to decide where to send users and tokens. mcpoauth reads saved copies and flags settings that the MCP authorization spec and OAuth 2.1 warn against: no PKCE S256, implicit or password grants, cleartext endpoints, tokens in URLs, a resource that does not match the server, broad scopes, and secrets or private keys published by mistake.

Standard library only. It never connects to a network; fetch the documents yourself (for example with curl) and point the tool at the files.

Rules

RuleSeverityWhat it flags
MO01criticalAuthorization server does not advertise PKCE S256 (field missing, or no S256)
MO02highPKCE plain method advertised
MO03highImplicit flow (response_type containing token, or implicit grant)
MO04highResource-owner password grant
MO05highhttp:// endpoint or identifier on a non-loopback host, including redirect_uris / post_logout_redirect_uris; file: / data: / javascript: schemes are flagged as critical
MO06mediumIssuer not https, or has a query or fragment
MO07highbearer_methods_supported includes query (tokens in URLs)
MO08high / mediumProtected resource metadata missing authorization_servers (high) or resource (medium)
MO09highresource does not match --resource-url (medium: has a fragment)
MO10mediumBroad scope advertised (*, all, admin, root, full_access, admin:org, delete_repo, write:packages, ...)
MO11criticalSecret or private key material in metadata (client_secret, private JWK members d/k/...)
MO12critical / highEndpoint on a cloud-metadata or link-local address (critical) or private IP / internal hostname (high)
MO13infoOpen dynamic client registration endpoint (MCP SHOULD support DCR; review confused-deputy risk for proxy servers)
MO14infoInventory of metadata documents found
MO15criticalJWT none algorithm advertised for token or request signing

Usage

python3 mcpoauth.py PATH [PATH ...] [--resource-url URL] [--json | --sarif]
                    [--min-severity LEVEL] [--fail-on LEVEL|none] [--disable RULE ...]
python3 mcpoauth.py --list-rules
# or, from a kit install:
agentsec mcpoauth examples/risky

After pip install of the kit, the same options work as agentsec mcpoauth …. Every tool also accepts --help and almost every tool accepts --json.

SARIF and CI

agentsec mcpoauth path/to/input --sarif > mcpoauth.sarif

# GitHub Actions (composite action ships with the repo)
- uses: dunkleschitz/agentsec@v0
  with:
    tools: mcpoauth
    paths: path/to/input
    fail-on: high

SARIF 2.1.0 can be uploaded to GitHub code scanning. The composite action writes per-tool reports under agentsec-sarif/ by default.

Known limits

  • It reads saved JSON only. It does not fetch metadata, follow authorization_servers,

validate JWKS signatures, or test the live flow (redirect URI checks, token audience validation, consent screens). Those need a dynamic test.

  • Document type is inferred from keys; an unusual document with neither resource

nor standard authorization-server keys is ignored.

  • MO09 compares scheme, host, and path (case-insensitive host, trailing slash ignored)

only when you pass --resource-url.

  • The broad-scope list (MO10) is a short heuristic list, not a policy.
  • Hostname classification for MO12 uses literal IPs and a few internal suffixes

(.internal, .local, .corp, ...); it does not resolve DNS.
